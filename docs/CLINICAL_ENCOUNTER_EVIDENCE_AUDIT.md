# Clinical Encounter Memory + Evidence Engine — Audit

Audited against `CLINICAL_ENCOUNTER_EVIDENCE_AUDIT_AND_BUILD.md`. Every claim below is traced to a real file/line, not inferred from names. Where a function/table has zero call sites outside its own tests, it is marked `SCAFFOLD`, not `COMPLETE`.

## A. Executive Summary

**PARTIALLY.**

The raw materials for the target product are real and working: local-first audio capture with per-word channel provenance, dual live/batch transcription with diarization refinement, durable per-word timestamp+speaker storage, a working PubMed/PMC evidence engine with scoring and citations, a clinician-cue capture UI, and a BAA-approval gate on network AI providers.

What does **not** exist is the thing the spec calls the product's actual moat: **segment-level transcript retrieval with dual (encounter + medical) provenance, surfaced through synthesis and UI.** Every path that currently touches the transcript for AI purposes (chat context hydration, the note-generation enhancer) discards per-word timestamps before the LLM ever sees them, and there was no `segment_id` concept anywhere in the schema. The structured-facts/conflict layer (`clinical_facts`, `clinical_fact_conflicts`, `reconcileEncounterEvidence()`) is schema-plus-a-pure-function with **zero runtime callers** — dead scaffold. There is no retrieval planner, no dual-provenance answer shape, and no "ask this encounter" UI distinct from the general chat panel.

**Update (pass 1):** segment-level transcript retrieval is now implemented — see `apps/desktop/src/clinical/encounter-retrieval.ts` and the new `search_encounter_transcript` chat tool. This is Milestone 2 (and the retrieval half of Milestone 3) from the Implementation Plan below.

**Update (pass 2):** both `search_clinical_evidence` and `search_encounter_transcript` now render as real citation cards in the chat UI instead of a raw JSON dump — see `chat/components/message/tool/search-clinical-evidence.tsx` and `search-encounter-transcript.tsx`. This closes gap #9 from the plan and is the first piece of "dual provenance... surviving all the way to the UI" (spec §14): a clinician can now see encounter segments (speaker + timestamp) and medical sources (PMID/DOI/journal/integrity status) as distinct, readable cards in the same chat thread. The retrieval planner, unified dual-provenance answer shape, and structured-facts wiring remain not built.

Also cleaned up real duplication in the evidence engine while working in this area: `sha256()` was independently reimplemented 5 times across `audit.ts`, `pmc.ts`, `pubmed.ts`, `phi-policy.ts`, and `repository.ts` — consolidated into `clinical/hash.ts`.

## D. Missing Critical Path

In dependency order — everything below this list is blocked on the item(s) above it:

1. **Segment-level transcript retrieval** (no `segment_id` concept exists anywhere; every current path either drops timestamps or returns whole-session blobs). This blocks:
2. **Ask-this-encounter with provenance** (needs #1 to cite exact segments).
3. **Retrieval planner** (needs #1 + the existing evidence retriever to route between them).
4. **Dual-provenance synthesis** (needs #2 + #3).
5. **Structured facts wiring** (`reconcileEncounterEvidence()` already works standalone — it just needs to be called against a real transcript+cues and persisted to the already-existing `clinical_facts`/`clinical_fact_conflicts` tables).
6. **Citation UI** (register `search_clinical_evidence` in the chat tool registry — small, independent of the above).

## E. Existing Code to Reuse (do not rewrite)

- `apps/desktop/src/stt/*` — capture lifecycle, live/batch transcription, diarization refinement. Solid.
- `transcripts.words_json` schema — has everything needed (`start_ms`, `end_ms`, `speaker_index`, text) to build segments from; no migration needed to add timing data, only to add a segmentation/index layer on top.
- `apps/desktop/src/clinical/pubmed.ts`, `pmc.ts`, `repository.ts`, `scoring.ts` — the entire evidence engine. Reuse `searchClinicalEvidence()` verbatim as the "evidence retriever" half of dual retrieval.
- `apps/desktop/src/clinical/reconciliation.ts` — the conflict-detection logic is correct per its tests; it just needs a caller and a persistence step, not a rewrite.
- `apps/desktop/src/clinical/cues.tsx` + `clinical_cues` table — reuse as-is as one of the source types for structured facts.
- `apps/desktop/src/chat/tools/*` pattern (`buildXTool()` + `withToolLogging` registration in `chat/tools/index.ts`) — reuse this exact pattern for a new encounter-retrieval tool.

## F. Legacy / Dead Code

- `apps/desktop/src/clinical/phi-policy.ts` (`decidePhiRoute`, `auditPhiRoute`) — fully orphaned. Either wire it into the real BAA-gated dispatch paths (`useLLMConnection.ts`, `useSTTConnection.ts`, and the future evidence-query path) so `clinical_phi_audit_events` actually records decisions, or remove it. Do not build new PHI-audit logging on top of it without first deciding which of `isBaaApproved()` vs `decidePhiRoute()` is the source of truth.
- `apps/desktop/src/clinical/repository.ts` `saveEvidenceLabel()` / `trainClinicalReranker()` — unreachable without a labeling UI. Not urgent; not on the critical path.
